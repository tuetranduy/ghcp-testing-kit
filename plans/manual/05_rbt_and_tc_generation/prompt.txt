---START---

Applying the **Risk-Based Testing (RBT)** strategy, generate a detailed list of Test Cases from the High-Level Scenarios reviewed in Step 4.

## Requirements for each Test Case:

### 1. Risk Assessment

Assess the **Risk Level** for each Module/Feature:
- **High Risk:** Core business, money/security related, many dependent users → Generate many test cases, test thoroughly
- **Medium Risk:** Important but not critical → Test moderately
- **Low Risk:** Secondary feature, low impact → Basic testing, happy path

### 2. Test Case structure

Each Test Case must include:

| Field | Requirement |
|-------|-------------|
| **Module / Sub-module** | The module name decomposed in Step 3 |
| **Test Case Title** | A short title with a clear purpose |
| **Pre-conditions** | Preconditions required before testing |
| **Test Steps** | The steps to perform, **numbered** |
| **Expected Results** | The expected result for each step, **numbered** |
| **Test Data** | Specific data (see the rule below) |
| **Priority** | High / Medium / Low |
| **Risk Level** | High / Medium / Low |

### 3. Test Data rules

Test Data **MUST BE SPECIFIC**; do not use generic descriptions:

```
❌ WRONG: "Enter a valid email"
✅ RIGHT: "Enter email: test_customer_01@domain.com"

❌ WRONG: "Enter a valid code"
✅ RIGHT: "Enter code: KH-2026-0012"

❌ WRONG: "Enter a phone number with the wrong format"
✅ RIGHT: "Enter phone: abc123xyz (letters instead of digits)"

❌ WRONG: "Enter a name that is too long"
✅ RIGHT: "Enter name: [a string of 256 consecutive 'A' characters] (exceeds the 255 limit)"
```

### 4. Coverage scope

Ensure the Test Cases cover a variety of cases:
- **Happy Path:** The main flow running smoothly
- **Negative Path:** Wrong input, missing data, wrong format
- **Boundary Values:** Boundary values (min, max, min-1, max+1)
- **Edge Cases:** Timeout, connection loss, concurrent access

[Additional hints (customize per project):
- Permissions: What user role A can and cannot do
- Compatibility: Responsive design, multi-browser
- Performance: Handling large lists (1000+ records)
- ...]

### 5. Field-Level Validation

**MANDATORY:** When a form/UI has input fields, you must:
1. **List all input fields** on the form/UI under test
2. **Generate separate validation TCs for EACH field** according to that field's specific characteristics
3. **Do NOT merge** validation of multiple fields into a single test case

Apply the validation checklist by field type:

| Field Type | Validation to test |
|---|---|
| **Text (Name, Address...)** | Required/Optional · Min length · Max length · Whitespace-only · Special characters (`<>&"'`) · XSS (`<script>alert(1)</script>`) · SQL injection (`' OR 1=1--`) · Unicode/Emoji · Leading/trailing spaces |
| **Email** | Valid format · Missing `@` · Missing domain · Invalid domain · Multiple `@` · Special characters · Max length · Case sensitivity · Duplicate email (if unique) |
| **Phone** | Digits only · Valid prefix (`+84`, `0`) · Min/Max length · Letters mixed in · `-`, `.`, spaces · Invalid area code |
| **Date / DateTime** | Correct format · Nonexistent date (`31/02`) · Leap year (`29/02/2024`) · Past/future · Min/Max date · Timezone |
| **Number / Currency** | Min/Max value · Negative · Zero · Decimals · Non-numeric characters · Overflow · Leading zeros · Currency format |
| **Dropdown / Select** | Default value · All options · Disabled option · Required (not selected) |
| **Checkbox / Radio** | Default state · Check/Uncheck · Required · Radio group (only 1) |
| **File Upload** | Valid/invalid file type · Max size · Empty file (0 KB) · Filename with special characters · Multiple files |
| **Password** | Min/Max length · Special characters · Uppercase/lowercase · Digits · Copy-paste · Show/hide · Confirm password |
| **Textarea** | Max length · Line breaks · HTML tags · Character counter |

**Field-Level Validation example for a "Registration" form:**
```
The form has 4 fields: Full name, Email, Phone, Password

→ "Full name" field (Text, max 100 chars, required):
  - TC: Leave empty → Show required error
  - TC: Enter 1 character → Valid (or show min length error)
  - TC: Enter 100 characters → Valid (max)
  - TC: Enter 101 characters → Show exceeds-max error
  - TC: Enter only whitespace → Show error
  - TC: Enter <script>alert(1)</script> → Script does not execute

→ "Email" field (Email, required, unique):
  - TC: Enter test@domain.com → Valid
  - TC: Enter testdomain.com (missing @) → Show format error
  - TC: Enter test@.com (missing domain) → Show error
  - TC: Enter an existing email → Show duplicate error

→ "Phone" field (Phone, 10 digits, starts with 0):
  - TC: Enter 0912345678 → Valid
  - TC: Enter 912345678 (missing prefix 0) → Show error
  - TC: Enter 091234567 (9 digits) → Show min length error
  - TC: Enter abc1234567 → Show digits-only error

→ "Password" field (Password, 8-20, requires uppercase + digit):
  - TC: Enter Abcdef12 (8 chars, has uppercase + digit) → Valid
  - TC: Enter abcdefgh (lowercase only) → Show error
  - TC: Enter 1234567 (7 chars) → Show min length error
```

> Determine each field's characteristics (type, required, min/max, format, unique...) from the requirements before generating TCs.

### 6. Test Design Techniques

Apply the following classic techniques to generate test cases systematically:

**a) Equivalence Partitioning**
Divide input data into equivalent groups; test only one representative value per group.
```
Example for the "Age" field (valid: 18-60):
- Valid class: 25 (represents 18-60)
- Invalid lower class: 10 (represents <18)
- Invalid upper class: 70 (represents >60)
```

**b) Boundary Value Analysis — BVA**
Test values at the boundaries: min, min+1, max-1, max, min-1, max+1.
```
Example for the "Password" field (6-20 characters):
- 5 characters (lower boundary -1) → Show error
- 6 characters (lower boundary)    → Valid
- 7 characters (lower boundary +1) → Valid
- 19 characters (upper boundary -1) → Valid
- 20 characters (upper boundary)    → Valid
- 21 characters (upper boundary +1) → Show error
```

**c) Decision Table**
Use it when logic has multiple combined conditions (AND/OR). List the condition combinations → result.
```
Example for the "Login" feature:
| Valid email | Correct password | Account active | Result           |
|:---:|:---:|:---:|---|
| ✅ | ✅ | ✅ | Login successful |
| ✅ | ❌ | ✅ | Show wrong password |
| ❌ | ✅ | ✅ | Show email does not exist |
| ✅ | ✅ | ❌ | Show account is locked |
```

**d) State Transition**
Use it for objects with multiple state transitions (workflow, order status...).
```
Example for Order status:
Newly created → Processing → Delivering → Completed
                           → Cancelled
Test: Each valid transition + the INVALID transitions (e.g., Completed → Newly created)
```

> Choose the technique that fits each Module/Field based on the data characteristics and business logic.
